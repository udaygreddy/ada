# ADA tests

Two kinds of test, because ADA has two kinds of behavior.

| | What it checks | How it runs |
|---|---|---|
| [`TEST-CASES.md`](TEST-CASES.md) | **Document validation** — positive and negative cases per document type | Judged by the model; compare its verdict to the expected column |
| [`PROMPTS.md`](PROMPTS.md) | **Ready-to-paste client messages** — one per case | Paste into a host with the skill installed, then check the verdict |
| [`run_gate_tests.sh`](run_gate_tests.sh) | **Code-enforced gates** — consent, hash binding, ledger integrity | Asserted by script; exits non-zero on failure |

The split mirrors the architecture: judgment is the model's job and can't be
asserted by a script, but the controls around it are deterministic and must
never regress.

## Run

```sh
python3 tests/make_fixtures.py     # writes tests/cases/ (39 folders, 42 files)
python3 tests/make_prompts.py      # writes tests/PROMPTS.md (39 client messages)
tests/run_gate_tests.sh            # code-enforced regressions — should be all PASS
```

Then walk [`TEST-CASES.md`](TEST-CASES.md) for the judgment cases.

## End-to-end, through a real host

To exercise a case the way a client would, print its prompt and paste it into
Claude (or any host with `adp-discovery` installed):

```sh
python3 tests/make_prompts.py payroll-register-prior-quarter
```

The prompt carries the company name, the ADP request, the payroll provider, the
drop folder and the reference date — everything Phase 0 and Phase A need — and
**never** the expected verdict. Check the skill's answer against
[`TEST-CASES.md`](TEST-CASES.md) afterwards.

## Case folders

One folder per case: `tests/cases/<descriptive-case-name>/`, holding the document(s) a client
would actually drop for that scenario. Point `enumerate.py` at a folder to
exercise it as a real drop folder.

**Filenames look like genuine exports** (`PayrollJournal_04012026-06302026.pdf`,
`Master_Control_by_Date_Range_20260720.csv`, `Form941_2026Q2.pdf`) — never like
test names. Folder names are descriptive for navigation (e.g.
`payroll-register-prior-quarter`) but never state the verdict — no
pass/fail/warn/good/bad in any folder name. That's deliberate: a fixture called
`register_fail_q1.pdf` could be "judged" from its filename without reading
anything. Realistic names force the judgment to come from content. Expected
verdicts live only in `TEST-CASES.md`, never inside a case folder.

`bank-proof-quickbooks-generated` is the clearest example —
`Direct_Deposit_Account_Summary.pdf` is *named* like a bank document; only the
content shows it was generated by QuickBooks and must be rejected.

All fixtures are **synthetic** and generated by `make_fixtures.py` — no real
client data. SSNs use the `000-` range the SSA never issues; EINs, routing and
account numbers are invented. They're committed so cases are reproducible, and
regenerating is idempotent (`--clean` to rebuild from scratch).

The corpus is built around reference date **2026-07-20** (mid-late July), which
per ADP's quarterly timing makes **Q2 2026 required** and **Q1 2026 fallback** —
so "Q2" fixtures pass the quarter checks and "Q1-only" fixtures fail them. Pass
`--ref-date 2026-07-20` when reproducing.

Two cases encode the subtle bits:

- Every register fixture ends with `Report generated on 07/20/2026` — a print
  date outside the quarter. Correct judgment ignores it and reads the check
  dates. This is the regression for the naive date-span bug that motivated
  model-judged validation.
- `employee-masterfile-complete` vs `employee-masterfile-masked-ssn` encode the
  evidence distinction the `ssn-unmasked` rule turns on: `▮▮▮` means the value
  was present and ADA masked it (good); a literal `XXX-XX-1234` means the
  source export was masked (bad, unusable by ADP).

## Adding cases

When a new rule goes into `ada/validations.yaml`, add a positive and a negative
case to `CASES` in `make_fixtures.py` (realistic filename, descriptive folder
name — no verdict words) and a row in `TEST-CASES.md` keyed to the rule id.
If the rule is code-enforced rather than judged, add an assertion to
`run_gate_tests.sh` instead.
